# To-Do Planner — MERN Architecture

## 1. Goal and scope

Build a beginner-friendly, single-user To-Do Planner using MongoDB, Express, React, and Node.js (MERN). Use JavaScript throughout. The first version runs locally and does not include authentication, collaboration, notifications, or recurring tasks.

Without authentication, anyone who can reach the API can access the same tasks. Keep this version local; add authentication and per-user task ownership before making it a private multi-user application.

## 2. Features

- Add a task with a required title and optional description.
- Choose Personal, Work, Study, Shopping, or Other as its category.
- Choose Low, Medium, or High as its priority.
- Set a required estimated duration in whole minutes.
- Set an optional due date.
- Edit task details and delete a task after confirmation.
- Mark a task completed or return it to pending.
- View all, pending, or completed tasks.
- Search by title and filter by category and priority.
- Display total, pending, and completed task counts.
- Persist tasks in MongoDB across browser refreshes and server restarts.

## 3. High-level architecture

```text
React frontend (browser)
        |
        | HTTP requests and JSON responses under /api
        v
Express API running on Node.js
        |
        | Mongoose queries and validation
        v
MongoDB database
```

React manages the interface. Express receives requests, validates data, and performs task operations. Mongoose defines the database schema and communicates with MongoDB. The browser never connects directly to MongoDB.

Use a Vite React frontend, an Express backend, and Mongoose. Use plain CSS and the browser's fetch API. Avoid Redux, microservices, and additional service/repository layers for this small first version.

## 5. Task data model

Store tasks in a MongoDB `tasks` collection. Each document represents one task.

| Field | Type | Rules |
| --- | --- | --- |
| `_id` | ObjectId | Generated by MongoDB; used for all task mutations. |
| `title` | String | Required; trimmed; 1–120 characters. |
| `description` | String | Optional; default empty string; maximum 2,000 characters. |
| `category` | String enum | Personal, Work, Study, Shopping, Other; default Other. |
| `priority` | String enum | Low, Medium, High; default Medium. |
| `durationMinutes` | Number | Required; positive safe integer. |
| `dueDate` | String or null | Optional; real calendar date in YYYY-MM-DD format; default null. |
| `completed` | Boolean | Default false. |
| `createdAt` | Date | Generated using Mongoose timestamps. |
| `updatedAt` | Date | Maintained using Mongoose timestamps. |

Store the due date as a date-only string because it represents a calendar day, not a time or timezone. Validate both its format and calendar validity. Avoid converting it to a UTC timestamp for display. A pending task is overdue when its due date is earlier than today's date in the browser's local timezone; tasks due today are not overdue.

Example API task:

```json
{
  "_id": "507f1f77bcf86cd799439011",
  "title": "Revise chapter 3",
  "description": "Review notes and answer practice questions.",
  "category": "Study",
  "priority": "High",
  "durationMinutes": 45,
  "dueDate": "2026-10-05",
  "completed": false,
  "createdAt": "2026-09-30T10:00:00.000Z",
  "updatedAt": "2026-09-30T10:00:00.000Z"
}
```

Do not store counts or separate pending/completed collections. Derive both from the tasks.

## 6. API contract

| Method | Path | Behavior | Success |
| --- | --- | --- | --- |
| GET | `/api/tasks` | Return all tasks, newest first. | 200 with `{ "tasks": [...] }` |
| POST | `/api/tasks` | Create a task from its details; initially pending. | 201 with `{ "task": {...} }` |
| PATCH | `/api/tasks/:id` | Update only supplied editable fields, including completion status. | 200 with `{ "task": {...} }` |
| DELETE | `/api/tasks/:id` | Delete the task. | 204 with no response body |
| GET | `/api/health` | Report service health without exposing secrets. | 200 when ready; 503 when the database is unavailable |

For POST, accept title, description, category, priority, durationMinutes, and dueDate. For PATCH, also allow completed. Reject unknown fields and empty updates. Never accept client-supplied IDs or timestamps. Normalize a blank optional due date to null. PATCH must preserve omitted fields and validate updated values.

Use 400 for invalid input or malformed task IDs, 404 for a valid ID that does not exist, and 500 for unexpected internal errors. Return a generic message for internal errors and log details only on the server.

Error response shape:

```json
{
  "error": {
    "message": "Please correct the task details.",
    "fields": {
      "title": "Title is required."
    }
  }
}
```

`fields` is optional. The frontend must handle non-JSON failures and must not try to parse a JSON body from a successful 204 deletion response.

## 7. Frontend state and data flow

Use React's useState and useEffect. No global state library is necessary.

State consists of:

- The full tasks array returned by the API.
- Search text, status view, category filter, and priority filter.
- The task being edited and the form values.
- Initial loading, mutation-in-progress, and error states.
- The task awaiting deletion confirmation.

Fetch all tasks on initial load. For this small application, calculate search results, filters, and counts in the browser. Search is a case-insensitive title substring match with surrounding search whitespace ignored. Combine all active filters using AND. Preserve the full tasks array when filtering.

Counts always describe all loaded tasks, independent of filters. Also show the number of visible results when filtering. Keep newest-created-first ordering consistent after edits.

For changes, wait for a successful API response before updating the tasks array. Add or replace the returned document using its ID; remove a deleted task after success. If a request fails, keep the existing data and form inputs and show a retryable error. Disable repeat submissions while a request is pending.

Completing a task in Pending view removes it from that view. Editing a task can also make it disappear from the current filtered view. Both are expected behavior.

## 8. Interface

Use a responsive single-page layout:

1. Page title and task counts.
2. Add/edit form with labeled controls and inline validation.
3. All / Pending / Completed view buttons.
4. Search, category, and priority controls with a Clear filters action.
5. Task cards showing details, status, and edit/delete/complete actions.
6. Confirmation dialog that names the task before deletion.

Reuse the same form for adding and editing. Editing must preserve completion status unless the user explicitly changes it through the completion action. Provide Cancel editing. Distinguish loading, empty collection, no matching results, and load failure. Use keyboard-accessible controls, visible focus indicators, and text labels for priority/status rather than color alone.

## 9. Edge cases and rules

| Case | Expected behavior |
| --- | --- |
| Empty or whitespace-only title | Reject after trimming. |
| Duplicate title | Allow; IDs distinguish tasks. |
| Extremely long text | Enforce limits on both frontend and backend; wrap text in cards. |
| Missing, zero, negative, fractional, or nonnumeric duration | Reject; require a positive safe integer. |
| Invalid category, priority, or completion type | Reject in the API, even if the UI normally prevents it. |
| Missing description or due date | Accept and apply defaults. |
| Invalid date such as February 30 | Reject; a format check alone is insufficient. |
| Past due date | Allow; label pending task overdue. |
| Completed task with past due date | Do not label it overdue. |
| Cancel deletion or editing | Leave persisted data unchanged. |
| Double-click submission | Disable the action while saving to reduce duplicate requests. |
| Database or network unavailable | Show an error and retry action; never falsely show success. |
| Refresh while filters are selected | Reload tasks; resetting filters is acceptable in version one. |
| Two browser tabs change the same task | Last successful update wins; refresh to see other-tab changes. Real-time sync is out of scope. |
| Task deleted elsewhere before an edit | Handle 404 with a clear message and offer to reload. |
| HTML-like text in title/description | Render as text; do not use dangerouslySetInnerHTML. |

## 10. Local configuration

Backend `.env.example` should document:

```dotenv
PORT=5000
MONGODB_URI=mongodb://127.0.0.1:27017/todo_planner
```

Use a Vite development proxy for `/api` requests to the backend, so frontend requests can use relative URLs. Keep the backend local for this first version. Do not enable unrestricted cross-origin access. Configure a separate allowed frontend origin if a future deployment requires it.

Keep real `.env` files, node_modules, build output, and credentials out of Git. Provide clear README steps for installing dependencies, starting MongoDB, creating the server environment file, and running client/server in separate terminals. A local MongoDB instance or a user-provided MongoDB Atlas connection may be used. Never put database credentials in frontend environment variables.

## 11. Implementation order

1. Scaffold client/server and document local setup.
2. Connect MongoDB, define the task schema, and implement the API.
3. Build task creation and the task list with loading and error states.
4. Add editing, deletion confirmation, and completion toggling.
5. Add counts, search, status views, and category/priority filters.
6. Add validation feedback, responsive styling, accessibility, and overdue labels.
7. Verify the main workflows and document results and any limitations.

## 12. Verification and acceptance criteria

- A valid task can be created and remains after a refresh.
- Defaults and optional fields work as documented.
- Editing changes only the intended fields.
- Canceling deletion keeps the task; confirming removes it permanently.
- Completion can be toggled in both directions.
- Combined filters and case-insensitive search return the expected tasks.
- Global counts remain correct during filtering and after mutations.
- Invalid input is rejected through both the UI and direct API requests.
- Failed requests leave existing tasks and unsaved form input intact.
- Date handling is correct for yesterday, today, leap days, and invalid dates.
- The interface is usable with a keyboard and on narrow screens.
- The frontend production build succeeds.

Use focused automated tests for API validation and CRUD behavior plus frontend filtering/count logic. API integration tests must use a separate disposable test database, never the user's development data. Perform a manual end-to-end check in a browser. Report any checks that could not run instead of claiming they passed.

## 13. Future extensions

Add authentication and per-user ownership, pagination/server-side filtering, reminders, and multi-device synchronization only after the first version works. These are intentionally outside the initial implementation.
